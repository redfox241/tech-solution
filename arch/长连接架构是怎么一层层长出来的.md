# 长连接架构，是怎么从一层长成三层的

2016 年夏天，我在一家做直播的公司值夜班。

凌晨两点，一次常规发版，三十多万人同时掉线，客服电话被打爆。第二天复盘，原因简单得让人无话可说：我们把业务代码和 WebSocket 服务打在了同一个包里，重启就等于所有人的连接一起断。

那次之后我一直在想一个问题：为什么长连接服务不能像普通 Web 服务那样，想重启就重启？

---

## 一、长连接到底麻烦在哪

普通 HTTP 请求，进来、算完、返回、断开，四步就忘了你是谁。宕了一台机器，下一台接着干，用户根本没感觉。

长连接不一样。TCP 一旦握上手，这根管子就拴在那台机器的内存里了。机器重启、进程被杀、网卡抖一下，管子就断。它不是数据库里那种换个连接还能重新读的数据，它是活的。

后来大家总结出一句话：**长连接不能迁移，只能重连。**

这一句话，几乎决定了后面所有的架构演进。

---

## 二、第一版：一个服务包打天下

2013 到 2016 年，大部分公司都这么干：一个进程，既负责握手、心跳、收发包，也负责聊天、房间、送礼、消息落库。

好处是快。三天能上线，出问题只有一个地方可查，小团队活得挺舒服。

坏处来得也快：

- **发版就掉线**。业务逻辑改一行，整个进程重启，在线的人全断。
- **业务 bug 直接打挂连接**。一次内存泄漏把进程 OOM 掉，五万人掉线。
- **没法按需扩容**。业务吃 CPU，连接吃内存，两种资源绑死在一起，扩容只能一起加，钱花得冤枉。
- **只能靠 sticky session 硬扛**，负载永远不均，热门节点先死。

这版适合什么？MVP、内网工具、几百人同时在线的场景。别嫌弃它，它救过不少项目的命。

## 三、第二版：把"连接"抽出去

大概是 2017 年前后，这层拆分开始普及。思路就一句话：**让管连接的人别管业务。**

前面一层叫接入网关，有的公司叫 connector，有的叫 access server。它只做几件很枯燥的事：握手、TLS 加解密、心跳、断线检测、协议编解码、消息转发。它连用户是谁都不太关心，只知道"这条连接对应哪个 uid"。

真正的业务在后面，走短连接 RPC 或者消息队列。

这一刀切下去，很多事立刻好了：

- **业务发版不再踢人**。业务服务重启，网关握着用户的连接，等它起来接着转发。
- **两种资源分开扩**。在线人数涨了加网关，业务量涨了加业务服务。
- **故障域变小**。业务服务挂了，用户只是暂时发不出消息，连接还在。

代价也得认：多了一跳转发，延迟多几毫秒；多了一套要维护的集群；网关自己变成了关键路径，必须做集群、做健康检查、做限流。

## 四、第三版：业务网关是怎么又冒出来的

两层用了两年，新的问题来了。而且这次不是技术问题，是组织问题。

业务从 3 个团队变成 12 个团队，每个团队都想直接对外开接口。于是鉴权写了 12 遍，限流写了 12 遍，日志格式 12 种，出了事故找不到是谁的责任。客户端那边更难受，一个 App 要连七八个域名。

于是又加了一层，业务网关，也叫 API 网关、BFF。所有请求从这里进，它干的是另一类活：验身份、拼参数、聚合几个服务的结果、限流熔断、灰度分流、打统一的日志和 trace id。

链路变成：客户端 → 接入路由 → 长连接网关 → 业务网关 → 业务服务。

这三层管的其实不是同一件事，很多人会混：

- **接入路由**：这条新连接该分给哪台机器
- **长连接网关**：这条连接怎么活下去
- **业务网关**：这个请求该不该放行、该发给谁

故障表现也完全不同。接入路由挂了，影响的是"新用户连不上"；长连接网关挂了，影响的是"连在这台机器上的用户断线"。分不清这两个，值班的时候就容易抓错人。

## 五、但每加一层，都要付账

这话我想说重一点：**分层不是免费的。**

- **延迟**。每多一跳，多一次序列化，多几毫秒。做实时对战、做语音，这几毫秒是要算账的。
- **排障难度**。一个请求穿过五个组件，trace id 对不上，你就只能靠猜。
- **成本**。一套集群三个环境，机器、监控、值班人力，都是钱。
- **组织成本**。多一层就多一个要协调的团队，多一份要写的规范。

我见过的翻车案例里，有一半是"上了三层网关，团队总共六个人"。

## 六、现在大家普遍怎么做

几个明显的变化：

1. **状态外置成了默认**。会话、房间、上下文都放 Redis 或者 KV，网关和业务服务都做成无状态，谁挂了都能换一台顶上。这套做法一上，sticky session 就可以关掉了。
2. **接入层越来越靠边**。云厂商的负载均衡、CDN 边缘节点开始原生支持 WebSocket 接入，长连接尽量在离用户最近的地方接住，回源的流量少很多。
3. **网关越做越薄**。只做协议转换和转发，复杂逻辑全部后移，"网关里带业务"是很多团队踩过的坑。
4. **重连变成了产品问题**。客户端做指数退避加随机抖动，服务端做断线消息补发，用户才真的感觉不到掉线。这块做不好，网关一抖就是一场景的重连风暴。

## 七、给正在做选型的人三句话

- 在线人数不到一万、团队不到五个人：**一层够用**。把代码写干净，比架构画得好看重要得多。
- 业务开始频繁发版、开始因为重启掉人：**拆出长连接网关**。这一步的收益最直接，性价比最高。
- 多个团队、多端接入、要对外开接口：**再上业务网关**。但先把 trace id 和限流规范统一了，不然它只是多了一跳，没解决任何事。

---

架构不是一次设计出来的，是长出来的。每一层背后都是某次事故、某次组织扩张留下的疤。

看到别人有五层，先别急着抄，问问他挨过几次打。
